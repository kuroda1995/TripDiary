## 1. システム概要

### 1.1 目的

TripDiary は、ユーザーが訪れた（または訪れたい）旅行スポットを写真と感想付きで記録し、他のユーザーと共有できる旅行記録・SNSアプリケーションである。
個人の旅の記録帳としての役割と、他ユーザーの投稿から次の旅先を見つける発見の場としての役割を両立する。

### 1.2 想定ユーザー

| ユーザー種別 | 説明 |
| --- | --- |
| ゲスト（未ログイン） | 公開投稿の閲覧・検索のみ可能 |
| 一般ユーザー（ログイン済み） | 投稿・いいね・コメント・フォロー・ステータス管理が可能 |

> 管理者機能（通報対応・ユーザー凍結等）は初期リリースのスコープ外とし、将来検討とする。

### 1.3 技術スタック

| レイヤー | 技術 |
| --- | --- |
| フロントエンド | React + TypeScript + Vite + Tailwind CSS + shadcn/ui |
| バックエンド | Java (Spring Boot) + Gradle + Spring Data JPA |
| データベース | PostgreSQL |
| 認証 | JWT（アクセストークン + リフレッシュトークン） |
| インフラ | AWS（S3: 画像保存 / RDS: PostgreSQL / ALB: ロードバランサ） |

### 1.4 システム構成（概要）

```
[Browser (React SPA)]
   │  HTTPS (REST/JSON, Authorization: Bearer <JWT>)
   ▼
[ALB] ──▶ [Spring Boot API] ──▶ [RDS (PostgreSQL)]
   │              │
   │              └─ 署名付きURL発行 (Presigned URL)
   │
   └─(画像を直接PUT)──▶ [S3]
```

## 2. 用語定義

| 用語 | 説明 |
| --- | --- |
| スポット | ユーザーが投稿する旅行先の記録。タイトル・場所・感想・写真を持つ |
| エリアタグ | スポットに付与する地域タグ（例: 「北海道」「京都」「沖縄」）。絞り込み検索に使用 |
| 行ってみたい！ | 他ユーザーのスポットに対する「いいね」に相当するリアクション |
| ステータス | ユーザーが各スポットに対して個人的に設定する状態。「訪問済み」「行きたい」の2種 |
| フォロー | 他ユーザーの投稿をタイムラインで追いかけるための関係 |

> **「行ってみたい！」と「行きたい」ステータスの違い**
> - 「行ってみたい！」= 投稿者への **公開リアクション**（件数が表示され、投稿者に伝わる）
> - 「行きたい」ステータス = 自分用の **個人リスト**（他人には件数のみ／非公開）
>
> UI上で混同しやすいため、ボタン文言・アイコンを明確に区別する。

## 3. 機能要件

機能IDの優先度は MoSCoW（**M**ust / **S**hould / **C**ould）で示す。

### 3.1 ユーザー認証（AUTH）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| AUTH-01 | 新規登録 | メールアドレス・ユーザー名・表示名・パスワードで登録する | M |
| AUTH-02 | 入力バリデーション | メール形式、ユーザー名（半角英数字と`_`、3〜30文字、一意）、パスワード（8〜72文字、英字と数字を各1文字以上含む） | M |
| AUTH-03 | ログイン | メールアドレス + パスワードで認証し、アクセストークン（JWT）とリフレッシュトークンを発行する | M |
| AUTH-04 | トークン更新 | リフレッシュトークンで新しいアクセストークンを発行する（リフレッシュトークンはローテーション） | M |
| AUTH-05 | ログアウト | サーバー側でリフレッシュトークンを失効させる | M |
| AUTH-06 | 認証ガード | 書き込み系API・マイページは認証必須。未認証時は 401 を返し、フロントはログイン画面へ遷移 | M |
| AUTH-07 | プロフィール編集 | 表示名・自己紹介・アイコン画像を変更できる | S |
| AUTH-08 | パスワード変更 | 現在のパスワード確認の上で変更できる。変更時は全リフレッシュトークンを失効 | S |
| AUTH-09 | 退会 | アカウントと関連データを削除する | C |
| AUTH-10 | パスワードリセット | メール経由のリセット | C（将来） |

### 3.2 スポット投稿 CRUD（SPOT）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| SPOT-01 | 投稿作成 | タイトル（必須・1〜100文字）、場所名（必須・1〜200文字）、エリアタグ（1〜5個）、感想（任意・最大5,000文字）、写真（0〜10枚）、訪問日（任意）を登録 | M |
| SPOT-02 | 投稿一覧 | 新着順で公開スポットを一覧表示（カーソル or ページング、1ページ20件） | M |
| SPOT-03 | 投稿詳細 | タイトル・場所・エリアタグ・感想・写真・投稿者・「行ってみたい！」数・コメント一覧を表示 | M |
| SPOT-04 | 投稿編集 | 投稿者本人のみ編集可能。写真の追加・削除・並び替えを含む | M |
| SPOT-05 | 投稿削除 | 投稿者本人のみ削除可能。関連するいいね・コメント・ステータス・写真レコードも削除し、S3オブジェクトは非同期で削除 | M |
| SPOT-06 | ユーザー別一覧 | 特定ユーザーの投稿一覧をプロフィール画面に表示 | M |
| SPOT-07 | 公開範囲 | 「公開」「非公開（自分のみ）」を選択可能 | S |
| SPOT-08 | 位置情報 | 緯度・経度を任意で保持し、地図表示に利用 | C（将来） |

### 3.3 写真アップロード（PHOTO）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| PHOTO-01 | 署名付きURL発行 | クライアントがファイル名・Content-Type・サイズを送信し、APIがS3の署名付きPUT URL（有効期限5分）とオブジェクトキーを返す | M |
| PHOTO-02 | 直接アップロード | クライアントは署名付きURLへ画像を直接PUTする（APIサーバーを経由しない） | M |
| PHOTO-03 | 投稿への紐付け | 投稿作成・編集時にオブジェクトキーを送信し、`spot_photos` に登録する。サーバー側でキーのプレフィックスが自ユーザーのものであることを検証 | M |
| PHOTO-04 | 制限 | 形式: JPEG / PNG / WebP / HEIC、1枚あたり最大10MB、1投稿あたり最大10枚 | M |
| PHOTO-05 | 表示 | 画像は CloudFront もしくは S3 の公開読み取り用URLから配信する | M |
| PHOTO-06 | 孤立ファイル削除 | 投稿に紐付かないまま24時間経過したS3オブジェクトはライフサイクルルール／バッチで削除 | S |
| PHOTO-07 | サムネイル生成 | 一覧用の縮小画像を生成（Lambda 等） | C（将来） |

### 3.4 いいね（「行ってみたい！」）（LIKE）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| LIKE-01 | いいね登録 | ログインユーザーはスポットに「行ってみたい！」を押せる。1ユーザー1スポットにつき1回まで | M |
| LIKE-02 | いいね解除 | 再度押すと解除される（トグル） | M |
| LIKE-03 | 件数表示 | 一覧・詳細に「行ってみたい！」数を表示。自分が押済みかどうかも返す | M |
| LIKE-04 | 自分の投稿 | 自分の投稿にも押せる（制限しない） | S |
| LIKE-05 | いいねした投稿一覧 | 自分が「行ってみたい！」した投稿の一覧を表示 | S |

### 3.5 コメント（COMMENT）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| CMT-01 | コメント投稿 | ログインユーザーはスポットにコメントできる（1〜1,000文字） | M |
| CMT-02 | コメント一覧 | スポット詳細で古い順に表示（ページング） | M |
| CMT-03 | コメント編集 | コメント投稿者本人のみ編集可能。編集済み表示を出す | S |
| CMT-04 | コメント削除 | コメント投稿者本人、またはスポット投稿者が削除可能 | M |
| CMT-05 | 返信（スレッド） | コメントへの返信 | C（将来） |

### 3.6 フォロー / フォロワー（FOLLOW）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| FLW-01 | フォロー | 他ユーザーをフォローできる。自分自身はフォロー不可 | M |
| FLW-02 | フォロー解除 | フォローを解除できる | M |
| FLW-03 | フォロー一覧 / フォロワー一覧 | 各ユーザーのフォロー中・フォロワーの一覧を表示 | M |
| FLW-04 | 件数表示 | プロフィールにフォロー数・フォロワー数・投稿数を表示 | M |

### 3.7 エリアタグ絞り込み検索（SEARCH）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| SRCH-01 | エリアタグ管理 | エリアタグはマスタとして管理する（初期データ: 47都道府県 + 主要海外エリア）。親子階層（地方 → 都道府県）を持つ | M |
| SRCH-02 | タグ絞り込み | エリアタグを1つ以上指定してスポットを絞り込む。複数指定時は OR 条件 | M |
| SRCH-03 | 親タグ検索 | 親タグ（例: 「関西」）を指定した場合、子タグ（「京都」「大阪」等）の投稿も含める | S |
| SRCH-04 | キーワード検索 | タイトル・場所名の部分一致検索 | S |
| SRCH-05 | 並び替え | 新着順 / 「行ってみたい！」数順 | S |
| SRCH-06 | ユーザー定義タグ | ユーザーが自由にタグを追加 | C（将来） |

### 3.8 スポットのステータス管理（STATUS）

| ID | 機能 | 詳細 | 優先度 |
| --- | --- | --- | --- |
| STS-01 | ステータス設定 | ログインユーザーは任意のスポット（自分・他人の投稿問わず）に「訪問済み」または「行きたい」を設定できる。1ユーザー1スポットにつき1ステータス | M |
| STS-02 | ステータス変更 | 「行きたい」→「訪問済み」等の切り替えが可能。訪問済みにした日時を記録 | M |
| STS-03 | ステータス解除 | ステータスを外せる | M |
| STS-04 | マイリスト | マイページで「訪問済み」「行きたい」それぞれの一覧を表示 | M |
| STS-05 | 公開範囲 | ステータスリストは本人のみ閲覧可能（初期仕様） | M |
| STS-06 | 自分の投稿の扱い | 自分の投稿作成時、デフォルトで「訪問済み」を自動設定する（OFF可） | C |

## 5. API 概要（参考）

ベースパス: `/api/v1`。リクエスト/レスポンスは JSON。
各 API のリクエスト・レスポンス例と業務ルールは [機能別ドキュメント](./features/README.md) を参照。

| メソッド | パス | 概要 | 認証 |
| --- | --- | --- | --- |
| POST | `/auth/signup` | 新規登録 | - |
| POST | `/auth/login` | ログイン（トークン発行） | - |
| POST | `/auth/refresh` | アクセストークン再発行 | - |
| POST | `/auth/logout` | ログアウト | 要 |
| GET | `/users/{username}` | プロフィール取得 | - |
| PATCH | `/users/me` | プロフィール更新 | 要 |
| GET | `/spots` | 一覧・検索（`areaIds`, `q`, `sort`, `cursor`） | - |
| POST | `/spots` | スポット作成 | 要 |
| GET | `/spots/{id}` | スポット詳細 | - |
| PUT | `/spots/{id}` | スポット更新 | 要（本人） |
| DELETE | `/spots/{id}` | スポット削除 | 要（本人） |
| POST | `/uploads/presigned-url` | S3署名付きURL発行 | 要 |
| PUT / DELETE | `/spots/{id}/like` | 行ってみたい！登録 / 解除 | 要 |
| GET / POST | `/spots/{id}/comments` | コメント一覧 / 投稿 | GET不要 / POST要 |
| PATCH / DELETE | `/comments/{id}` | コメント編集 / 削除 | 要 |
| PUT / DELETE | `/users/{username}/follow` | フォロー / 解除 | 要 |
| GET | `/users/{username}/following`, `/followers` | 一覧 | - |
| PUT / DELETE | `/spots/{id}/status` | ステータス設定（body: `VISITED`/`WANT_TO_GO`） / 解除 | 要 |
| GET | `/me/spot-statuses?status=` | マイリスト | 要 |
| GET | `/timeline` | フォロー中タイムライン | 要 |
| GET | `/areas` | エリアタグ一覧（階層） | - |

エラーレスポンスは共通形式とする:

```json
{ "code": "SPOT_NOT_FOUND", "message": "指定されたスポットは存在しません", "details": [] }
```

## 6. 非機能要件

### 6.1 性能

| ID | 要件 |
| --- | --- |
| NFR-PERF-01 | 一覧・詳細APIの応答時間は 95パーセンタイルで 500ms 以内（画像転送を除く） |
| NFR-PERF-02 | 一覧APIはページングを必須とし、1リクエストの最大取得件数は50件 |
| NFR-PERF-03 | N+1 問題を回避する（JPA の fetch join / `@EntityGraph` / バッチフェッチを使用） |
| NFR-PERF-04 | 画像はAPIサーバーを経由せず S3 へ直接アップロード・配信する |
| NFR-PERF-05 | 初期想定規模: ユーザー1万人、スポット10万件、同時接続100程度 |

### 6.2 可用性・拡張性

| ID | 要件 |
| --- | --- |
| NFR-AVL-01 | API サーバーはステートレスとし、ALB 配下で水平スケール可能にする（セッションを持たない） |
| NFR-AVL-02 | RDS は本番環境で Multi-AZ 構成とする |
| NFR-AVL-03 | 稼働率目標 99.5%（計画メンテナンスを除く） |
| NFR-AVL-04 | ALB ヘルスチェック用エンドポイント（`/actuator/health`）を用意する |

### 6.3 セキュリティ

| ID | 要件 |
| --- | --- |
| NFR-SEC-01 | 全通信を HTTPS 化（ALB で TLS 終端、ACM 証明書を使用） |
| NFR-SEC-02 | パスワードは BCrypt（コスト10以上）でハッシュ化して保存。平文・可逆暗号は禁止 |
| NFR-SEC-03 | アクセストークン有効期限: 15分 / リフレッシュトークン有効期限: 14日。リフレッシュトークンは DB にハッシュ値で保存し、使用時にローテーションする |
| NFR-SEC-04 | JWT 署名鍵は AWS Secrets Manager 等で管理し、ソースコード・リポジトリに含めない |
| NFR-SEC-05 | リソース所有者チェック（編集・削除は本人のみ）をサービス層で必ず実施する |
| NFR-SEC-06 | 入力値はサーバー側で Bean Validation により検証する。SQL は JPA / プリペアドステートメントのみ使用 |
| NFR-SEC-07 | XSS 対策: 感想・コメントはプレーンテキストとして扱い、フロントでエスケープ表示（`dangerouslySetInnerHTML` 禁止） |
| NFR-SEC-08 | CORS は許可オリジンを明示的に限定する |
| NFR-SEC-09 | S3 バケットはパブリック書き込み不可。アップロードは署名付きURLのみ、Content-Type とサイズ上限を署名条件に含める |
| NFR-SEC-10 | ログイン API にレート制限を設ける（例: 同一IPから5分間に10回まで） |
| NFR-SEC-11 | ログにパスワード・トークン等の機密情報を出力しない |

### 6.4 保守性・運用

| ID | 要件 |
| --- | --- |
| NFR-OPS-01 | DB スキーマは Flyway でバージョン管理する（`spring.jpa.hibernate.ddl-auto=validate`） |
| NFR-OPS-02 | 環境は local / staging / production の3つ。設定は Spring Profile と環境変数で切り替える |
| NFR-OPS-03 | 本番のアプリケーションログは Logback で JSON 形式（構造化ログ）を標準出力へ出し、CloudWatch Logs に集約する。ログレベル（INFO / WARN / ERROR）の使い分けは [rules.md](./rules.md#5-ログ規約) に従う |
| NFR-OPS-04 | RDS の自動バックアップを有効化し、保持期間は7日以上 |
| NFR-OPS-05 | API 仕様は springdoc-openapi（OpenAPI 3.0）でコントローラーのアノテーションから自動生成し、Swagger UI（`/swagger-ui/index.html`）で確認できること |
| NFR-OPS-06 | ローカル開発は Docker Compose で PostgreSQL を起動できること |
| NFR-OPS-07 | MDC により `requestId`・`userId` を全ログに自動付与し、リクエスト単位で追跡できること |
| NFR-OPS-08 | Datadog 等の外部有償 APM は使用せず、CloudWatch Logs / Alarm と Spring Boot Actuator で監視する |

### 6.5 品質・テスト

| ID | 要件 |
| --- | --- |
| NFR-QA-01 | バックエンド: JUnit 5 + Mockito による単体テスト、Testcontainers（PostgreSQL）による結合テスト |
| NFR-QA-02 | フロントエンド: Vitest + React Testing Library による単体テスト |
| NFR-QA-03 | テストカバレッジ目標: BE Service 層 80% 以上、BE 全体・FE 70% 以上 |
| NFR-QA-04 | Lint / Format: ESLint + Prettier（フロント）、Spotless or Checkstyle（バックエンド） |
| NFR-QA-05 | 機能実装ごとに単体・結合テストを作成し、オールグリーンを確認してから完了とする |
| NFR-QA-06 | GitHub Actions で PR 作成時・push 時に単体・結合・E2E（Playwright）テストを自動実行する |
| NFR-QA-07 | 負荷テスト（k6）は全機能完成時に1回のみ手動トリガーで実施し、日々の CI では実行しない |

詳細は [qa_test_plan.md](./qa_test_plan.md) を参照。

### 6.6 ユーザビリティ・互換性

| ID | 要件 |
| --- | --- |
| NFR-UX-01 | レスポンシブ対応（スマートフォン幅 375px 〜 デスクトップ） |
