| 項目 | 内容 |

## 1. 概要

メールアドレスとパスワードによる新規登録・ログインを提供します。認証には JWT を使い、サーバーはセッションを持ちません（ステートレス）。

| トークン | 有効期限 | 保存場所（サーバー） | 保存場所（ブラウザ） | 用途 |
| --- | --- | --- | --- | --- |
| アクセストークン（JWT, HS256） | 15分 | 保存しない | メモリのみ（JavaScript の変数） | API 呼び出し時の `Authorization` ヘッダ |
| リフレッシュトークン（32バイト乱数） | 14日 | `refresh_tokens` に SHA-256 ハッシュで保存 | HttpOnly Cookie `refresh_token` | アクセストークンの再発行 |

### トークンの保存場所の方針

- **アクセストークンは localStorage に保存しない。** XSS でスクリプトを実行された場合に盗まれるため。ページを再読み込みするとメモリから消えるが、起動時にリフレッシュトークンで復元する。
- **リフレッシュトークンは HttpOnly Cookie に保存する。** JavaScript から読めないため XSS で盗まれない。属性は以下のとおり。

| 属性 | 値 | 理由 |
| --- | --- | --- |
| `HttpOnly` | あり | JavaScript から読めないようにする |
| `Secure` | あり（ローカル開発の `local` プロファイルのみなし） | HTTPS 以外で送らない |
| `SameSite` | `Strict` | 他サイトからのリクエストに付かない（CSRF 対策） |
| `Path` | `/api/v1/auth` | 認証 API にだけ送られ、通常の API リクエストには付かない |
| `Max-Age` | 14日 | リフレッシュトークンの有効期限と同じ |

## 2. ユーザーストーリー

- ゲストとして、メールアドレスで会員登録して、旅の記録を投稿できるようになりたい。
- ユーザーとして、ログインして自分のアカウントで操作したい。
- ユーザーとして、毎回ログインし直さなくても一定期間ログイン状態を保ちたい。
- ユーザーとして、共用の端末ではログアウトしてアカウントを守りたい。
- ユーザーとして、表示名・自己紹介・アイコンを変更したい。

## 3. 画面・UI

| 画面 | パス | 主な要素 |
| --- | --- | --- |
| 新規登録 | `/signup` | メールアドレス、ユーザー名、表示名、パスワード、パスワード確認、登録ボタン |
| ログイン | `/login` | メールアドレス、パスワード、ログインボタン、新規登録へのリンク |
| マイページ | `/me` | アイコン・表示名・ユーザー名・自己紹介・メールアドレス、プロフィール編集・パスワード変更へのリンク、マイリストのタブ（行きたい / 訪問済み / 行ってみたい！した投稿。[08_spot_status.md](08_spot_status.md)）（ログイン必須） |
| プロフィール編集 | `/settings/profile` | アイコン画像（選択・削除）、表示名、自己紹介（文字数カウンタ付き）、保存ボタン（ログイン必須） |
| パスワード変更 | `/settings/password` | 現在のパスワード、新しいパスワード、新しいパスワード（確認）（ログイン必須） |

- アイコン画像は選んだ時点で S3 へアップロードし（`purpose: AVATAR`、5MB まで、HEIC は JPEG に変換）、保存ボタンでプロフィールに反映します。アップロード中は保存ボタンを押せません。
- アイコンはヘッダー・マイページ・スポットの投稿者欄に表示します。未設定の場合は表示名の先頭1文字を表示します。
- 保存後はヘッダーの表示名・アイコンをすぐに更新します。

- 入力エラーは各フィールドの直下に表示します（React Hook Form + Zod でクライアント側でも検証）。サーバーの入力エラー（`details`）・重複エラー（`EMAIL_ALREADY_EXISTS` など）も該当する項目に表示します。
- 未ログインで認証が必要な画面にアクセスした場合は `/login?redirect=<元のパス>` に遷移し、ログイン後に元の画面へ戻します。`redirect` はサイト内のパスのみ受け付けます（オープンリダイレクト対策）。
- ログイン済みでログイン・新規登録画面を開いた場合は、`redirect` の画面（なければトップ）へ移動します。
- アクセストークンの期限切れ（401 `TOKEN_EXPIRED`）を受けた場合、フロントエンドは自動でリフレッシュして元のリクエストを1回だけ再実行します。同時に複数のリクエストが期限切れになっても、リフレッシュは1回にまとめます（リフレッシュトークンは使い捨てで、二重に使うと再利用検知で全トークンが失効するため）。
- リフレッシュにも失敗した場合は未ログイン状態に戻します。
- ヘッダーには、未ログインなら「ログイン」「新規登録」、ログイン中なら表示名（マイページへのリンク）と「ログアウト」を表示します。

## 4. API 仕様

| メソッド | パス | 認証 | 概要 |
| --- | --- | --- | --- |
| POST | `/auth/signup` | 不要 | 新規登録 |
| POST | `/auth/login` | 不要 | ログイン |
| POST | `/auth/refresh` | 不要（Cookie） | トークン再発行 |
| POST | `/auth/logout` | 不要（Cookie） | ログアウト |
| GET | `/users/me` | 必要 | ログイン中のユーザー情報 |
| PATCH | `/users/me` | 必要 | プロフィール更新 |
| PUT | `/users/me/password` | 必要 | パスワード変更 |

### 4.1 新規登録 `POST /auth/signup`

リクエスト:

```json
{
  "email": "taro@example.com",
  "username": "taro_trip",
  "displayName": "旅するタロウ",
  "password": "Passw0rd123"
}
```

レスポンス `201 Created`（登録と同時にログイン状態にする）:

```http
Set-Cookie: refresh_token=Xk3...; Path=/api/v1/auth; Max-Age=1209600; HttpOnly; Secure; SameSite=Strict
Cache-Control: no-store
```

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "user": {
    "id": 42,
    "email": "taro@example.com",
    "username": "taro_trip",
    "displayName": "旅するタロウ",
    "bio": null,
    "avatarUrl": null
  }
}
```

リフレッシュトークンはレスポンス本文には含めず、Cookie でのみ返します。

### 4.2 ログイン `POST /auth/login`

リクエスト: `{ "email": "taro@example.com", "password": "Passw0rd123" }`
レスポンス `200 OK`: 新規登録と同じ形式（Cookie も同様に設定）。

### 4.3 トークン再発行 `POST /auth/refresh`

リクエスト: 本文なし。ブラウザが `refresh_token` Cookie を自動で送信します。
レスポンス `200 OK`: 新規登録と同じ形式。Cookie も **新しい** リフレッシュトークンに置き換えます（古いものは失効）。

### 4.4 ログアウト `POST /auth/logout`

リクエスト: 本文なし（`refresh_token` Cookie を送信）。
レスポンス `204 No Content`。リフレッシュトークンを失効させ、`Max-Age=0` で Cookie を削除します。Cookie が無い・失効済みでも 204 を返します（冪等）。

### 4.5 ログイン中のユーザー `GET /users/me`

レスポンス `200 OK`: 4.1 の `user` と同じ形式。

### 4.6 プロフィール更新 `PATCH /users/me`

リクエスト（変更する項目のみ）:

```json
{ "displayName": "タロウ", "bio": "週末は温泉めぐり♨", "avatarS3Key": "avatars/42/3b1f....webp" }
```

| 項目 | 送らない | `null` | 値あり |
| --- | --- | --- | --- |
| `displayName` | 変更しない | エラー（`VALIDATION_ERROR`） | 前後の空白を除いて保存 |
| `bio` | 変更しない | 削除 | 前後の空白を除いて保存（空白のみなら削除） |
| `avatarS3Key` | 変更しない | アイコンを削除 | [署名付き URL 発行](03_photo_upload.md)（`purpose: AVATAR`）で受け取ったキーに差し替え |

レスポンス `200 OK`: 更新後のユーザー情報（4.1 の `user` と同じ形式）。差し替え・削除したアイコンのファイルは、コミット後に S3 から削除します。

### 4.7 パスワード変更 `PUT /users/me/password`

リクエスト: `{ "currentPassword": "Passw0rd123", "newPassword": "NewPass456" }`

レスポンス `200 OK`: 新規登録と同じ形式（Cookie も新しいリフレッシュトークンに置き換える）。全リフレッシュトークンを失効させてから、この端末用に新しいトークンを発行するため、操作した端末はログインしたままで、他の端末はログアウトされます（他の端末のアクセストークンは JWT のため、有効期限の15分までは使えます）。

## 5. 業務ルール・バリデーション

| 項目 | ルール |
| --- | --- |
| メールアドレス | 必須、メール形式、最大255文字、大文字小文字を区別せず一意 |
| ユーザー名 | 必須、半角英数字と `_` のみ、3〜30文字、大文字小文字を区別せず一意。登録後は変更不可（URL に使うため） |
| 表示名 | 必須、1〜50文字 |
| パスワード | 必須、8〜72文字の半角英数字・記号（`!`〜`~`）、英字と数字をそれぞれ1文字以上含む。BCrypt は72バイトまでしか扱えないため、全角文字（1文字3バイト）は使えない |
| 自己紹介 | 任意、最大500文字 |
| アイコン | `avatars/{自分のuserId}/{UUID}.{拡張子}` のキーで、S3 上に実在し、JPEG / PNG / WebP / HEIC・5MB 以内であること |
| パスワード保存 | BCrypt（コスト10以上）でハッシュ化。平文は保存・ログ出力しない |
| ログイン失敗 | メールアドレスが存在しない場合もパスワード誤りの場合も同じエラー（アカウントの存在を推測させない）。存在しない場合もダミーのパスワード照合を行い、応答時間の差も出さない |
| レート制限 | 同一 IP からのログインは5分間に10回まで。超過時は 429。カウンタは API サーバーのメモリ上にあるため、複数台構成では1台あたりの上限になる。本番では ALB の `X-Forwarded-For` からクライアント IP を取得する |
| リフレッシュ | 使用したリフレッシュトークンは使用済み（`rotated_at`）にし、新しいトークンを発行（ローテーション）。使用済みトークンの再利用は、使用済みになってから **猶予期間（既定30秒、`app.jwt.refresh-reuse-grace`）** の間だけ許し、新しいトークンを発行する（更新の応答を受け取る前に画面を移った・複数タブで同時に更新した場合にログアウトさせないため）。猶予期間を過ぎた使用済みトークン、またはログアウト等で失効（`revoked_at`）したトークンが再利用された場合は、そのユーザーの全リフレッシュトークンを失効させる（盗用対策） |
| ログアウト | 送られたリフレッシュトークンを失効させ、猶予期間中の使用済みトークン（直前の更新で交換した古いトークンなど）もあわせて失効させる（ログアウト後に古いトークンで再びログインできないようにする） |
| パスワード変更 | 現在のパスワードの確認が必須。現在と同じパスワードには変更できない。変更後は全リフレッシュトークンを失効させ、操作した端末にだけ新しいトークンを発行する。アクセストークンを盗まれた場合の総当たり対策として、同一ユーザーは5分間に10回まで（ログインと同じ制限の仕組み） |

## 7. エラーコード

| HTTP | コード | 発生条件 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 入力形式の誤り |
| 400 | `INVALID_AVATAR_KEY` | 他人のキー・スポット写真のキー・S3 に存在しない・対応外の形式・5MB 超のアイコン |
| 400 | `INVALID_CURRENT_PASSWORD` | パスワード変更で現在のパスワードが違う |
| 400 | `PASSWORD_UNCHANGED` | 新しいパスワードが現在のパスワードと同じ |
| 401 | `INVALID_CREDENTIALS` | メールアドレスまたはパスワードが違う |
| 401 | `TOKEN_EXPIRED` | アクセストークンの期限切れ |
| 401 | `INVALID_TOKEN` | トークンの改ざん・署名不一致・形式不正 |
| 401 | `INVALID_REFRESH_TOKEN` | リフレッシュトークンが存在しない・期限切れ・失効済み |
| 409 | `EMAIL_ALREADY_EXISTS` | メールアドレスが登録済み |
| 409 | `USERNAME_ALREADY_EXISTS` | ユーザー名が使用済み |
| 409 | `DATA_CONFLICT` | 同じメールアドレス・ユーザー名での登録がほぼ同時に行われた（一意制約違反） |
| 429 | `TOO_MANY_REQUESTS` | ログイン・パスワード変更の試行回数の超過 |

## 8. テスト観点

[品質チェック・テスト計画書 4.1](../qa_test_plan.md#41-ユーザー認証auth) を参照。特に以下を重点的に確認します。

- パスワードがハッシュ化されて保存され、レスポンス・ログに含まれないこと
- 期限切れ・改ざんされた JWT が拒否されること
- リフレッシュトークンのローテーションと再利用検知
- 大文字小文字違いのメールアドレス・ユーザー名で重複登録できないこと

## 9. 補足・将来検討

- 他のユーザーのプロフィール（自己紹介など）を見る画面・API（`GET /users/{username}`）は、フォロー機能（[06_follow.md](06_follow.md)）で追加しました。
- PATCH の「送らない」と「null」を区別するため、`ProfileUpdateRequest` は record ではなく setter で受けるクラスにしています（record のコンストラクタだと、送らなかった項目も `Optional.empty()` になるため）。
- パスワードリセット（メール送信）は将来対応（AUTH-10）。
- ソーシャルログイン（Google 等）は将来検討。
- 以前は、リロード直後に画面を移る・複数タブでほぼ同時に更新すると、再利用検知で全トークンが失効してログアウトされることがありました。使用済みトークンの再利用に猶予期間を設けて解消しています（5章「リフレッシュ」）。猶予期間中は、盗まれた使用済みトークンも使えてしまうため、長くしすぎないこと。
