# 01. ユーザー認証（AUTH）

| 項目 | 内容 |
| --- | --- |
| 機能ID | AUTH-01 〜 AUTH-10 |
| 関連テーブル | `users`, `refresh_tokens` |
| 関連資料 | [要件定義書 3.1](../requirements.md#31-ユーザー認証auth) / [アーキテクチャ 4.1](../architecture.md#41-jwt-認証フロー) |

---

## 1. 概要

メールアドレスとパスワードによる新規登録・ログインを提供します。認証には JWT を使い、サーバーはセッションを持ちません（ステートレス）。

| トークン | 有効期限 | 保存場所（サーバー） | 用途 |
| --- | --- | --- | --- |
| アクセストークン（JWT） | 15分 | 保存しない | API 呼び出し時の `Authorization` ヘッダ |
| リフレッシュトークン | 14日 | `refresh_tokens` に SHA-256 ハッシュで保存 | アクセストークンの再発行 |

## 2. ユーザーストーリー

- ゲストとして、メールアドレスで会員登録して、旅の記録を投稿できるようになりたい。
- ユーザーとして、ログインして自分のアカウントで操作したい。
- ユーザーとして、毎回ログインし直さなくても一定期間ログイン状態を保ちたい。
- ユーザーとして、共用の端末ではログアウトしてアカウントを守りたい。
- ユーザーとして、表示名・自己紹介・アイコンを変更したい。

## 3. 画面・UI

| 画面 | パス | 主な要素 |
| --- | --- | --- |
| 新規登録 | `/signup` | メールアドレス、ユーザー名、表示名、パスワード、パスワード確認、登録ボタン |
| ログイン | `/login` | メールアドレス、パスワード、ログインボタン、新規登録へのリンク |
| プロフィール編集 | `/settings/profile` | 表示名、自己紹介、アイコン画像、保存ボタン |
| パスワード変更 | `/settings/password` | 現在のパスワード、新しいパスワード |

- 入力エラーは各フィールドの直下に表示します（React Hook Form + Zod でクライアント側でも検証）。
- 未ログインで認証が必要な画面にアクセスした場合は `/login?redirect=<元のパス>` に遷移し、ログイン後に元の画面へ戻します。
- アクセストークンの期限切れ（401 `TOKEN_EXPIRED`）を受けた場合、フロントエンドは自動でリフレッシュして元のリクエストを再実行します。

## 4. API 仕様

| メソッド | パス | 認証 | 概要 |
| --- | --- | --- | --- |
| POST | `/auth/signup` | 不要 | 新規登録 |
| POST | `/auth/login` | 不要 | ログイン |
| POST | `/auth/refresh` | 不要 | トークン再発行 |
| POST | `/auth/logout` | 必要 | ログアウト |
| GET | `/users/me` | 必要 | ログイン中のユーザー情報 |
| PATCH | `/users/me` | 必要 | プロフィール更新 |
| PUT | `/users/me/password` | 必要 | パスワード変更 |

### 4.1 新規登録 `POST /auth/signup`

リクエスト:

```json
{
  "email": "taro@example.com",
  "username": "taro_trip",
  "displayName": "旅するタロウ",
  "password": "Passw0rd123"
}
```

レスポンス `201 Created`（登録と同時にログイン状態にする）:

```json
{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "d1f0c3a8-...",
  "expiresIn": 900,
  "user": { "id": 42, "username": "taro_trip", "displayName": "旅するタロウ", "avatarUrl": null }
}
```

### 4.2 ログイン `POST /auth/login`

リクエスト: `{ "email": "taro@example.com", "password": "Passw0rd123" }`
レスポンス `200 OK`: 新規登録と同じ形式。

### 4.3 トークン再発行 `POST /auth/refresh`

リクエスト: `{ "refreshToken": "d1f0c3a8-..." }`
レスポンス `200 OK`: 新しい `accessToken` と **新しい** `refreshToken`（古いものは失効）。

### 4.4 ログアウト `POST /auth/logout`

リクエスト: `{ "refreshToken": "d1f0c3a8-..." }`
レスポンス `204 No Content`。

### 4.5 プロフィール更新 `PATCH /users/me`

リクエスト（変更する項目のみ）:

```json
{ "displayName": "タロウ", "bio": "週末は温泉めぐり♨", "avatarS3Key": "avatars/42/3b1f....webp" }
```

レスポンス `200 OK`: 更新後のユーザー情報。

## 5. 業務ルール・バリデーション

| 項目 | ルール |
| --- | --- |
| メールアドレス | 必須、メール形式、最大255文字、大文字小文字を区別せず一意 |
| ユーザー名 | 必須、半角英数字と `_` のみ、3〜30文字、大文字小文字を区別せず一意。登録後は変更不可（URL に使うため） |
| 表示名 | 必須、1〜50文字 |
| パスワード | 必須、8〜72文字、英字と数字をそれぞれ1文字以上含む（72文字は BCrypt の上限） |
| 自己紹介 | 任意、最大500文字 |
| パスワード保存 | BCrypt（コスト10以上）でハッシュ化。平文は保存・ログ出力しない |
| ログイン失敗 | メールアドレスが存在しない場合もパスワード誤りの場合も同じエラー（アカウントの存在を推測させない） |
| レート制限 | 同一 IP からのログインは5分間に10回まで。超過時は 429 |
| リフレッシュ | 使用したリフレッシュトークンは失効させ、新しいトークンを発行（ローテーション）。失効済みトークンが再利用された場合は、そのユーザーの全リフレッシュトークンを失効させる（盗用対策） |
| パスワード変更 | 現在のパスワードの確認が必須。変更後は全リフレッシュトークンを失効 |

## 6. 関連テーブル

| テーブル | 用途 |
| --- | --- |
| `users` | ユーザー情報（メール・ユーザー名・パスワードハッシュ・プロフィール） |
| `refresh_tokens` | リフレッシュトークンのハッシュ・有効期限・失効日時 |

## 7. エラーコード

| HTTP | コード | 発生条件 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 入力形式の誤り |
| 401 | `INVALID_CREDENTIALS` | メールアドレスまたはパスワードが違う |
| 401 | `TOKEN_EXPIRED` | アクセストークンの期限切れ |
| 401 | `INVALID_TOKEN` | トークンの改ざん・署名不一致・形式不正 |
| 401 | `INVALID_REFRESH_TOKEN` | リフレッシュトークンが存在しない・期限切れ・失効済み |
| 409 | `EMAIL_ALREADY_EXISTS` | メールアドレスが登録済み |
| 409 | `USERNAME_ALREADY_EXISTS` | ユーザー名が使用済み |
| 429 | `TOO_MANY_REQUESTS` | ログイン試行回数の超過 |

## 8. テスト観点

[品質チェック・テスト計画書 4.1](../qa_test_plan.md#41-ユーザー認証auth) を参照。特に以下を重点的に確認します。

- パスワードがハッシュ化されて保存され、レスポンス・ログに含まれないこと
- 期限切れ・改ざんされた JWT が拒否されること
- リフレッシュトークンのローテーションと再利用検知
- 大文字小文字違いのメールアドレス・ユーザー名で重複登録できないこと

## 9. 補足・将来検討

- パスワードリセット（メール送信）は将来対応（AUTH-10）。
- ソーシャルログイン（Google 等）は将来検討。
- リフレッシュトークンをフロントエンドのどこに保存するか（HttpOnly Cookie を推奨）は実装時に決定します。
