## 1. 品質方針

1. **開発スピードより品質とエラー撲滅を最優先とする。**
2. **機能を実装するたびに、その機能の単体テスト・結合テストを作成・実行し、オールグリーンを確認してから完了とする。** テストのない機能実装はレビュー対象外とする。
3. テストは CI（GitHub Actions）で PR 作成時・push 時に自動実行し、1件でも失敗した PR はマージしない。
4. **負荷テストは日々の CI で実行しない。** 全機能完成時に1回のみ、手動トリガーで実施する（[6章](#6-パフォーマンステスト負荷テスト)）。

## 2. テストレベルと範囲

| レベル | 対象 | ツール | 実行タイミング |
| --- | --- | --- | --- |
| 静的解析 | 全コード | oxlint / Prettier / `tsc -b`（FE）、Spotless（BE） | ローカル・CI（毎回） |
| 単体テスト（BE） | Service / Domain / Util / JWT 処理 | JUnit 5, Mockito, AssertJ | ローカル・CI（毎回） |
| 単体テスト（FE） | コンポーネント / hooks / utils | Vitest, React Testing Library, MSW | ローカル・CI（毎回） |
| 結合テスト（BE） | Controller〜Repository〜DB を通した API 単位 | `@SpringBootTest` + MockMvc, Testcontainers (PostgreSQL, S3Mock) | ローカル・CI（毎回） |
| リポジトリテスト | JPA クエリ・制約 | `@DataJpaTest` + Testcontainers | ローカル・CI（毎回） |
| E2E テスト | ブラウザ操作による主要ユーザーシナリオ | Playwright（Chromium） + Docker Compose | CI（毎回） |
| 負荷テスト | 主要 API | k6 | **全機能完成時に1回のみ・手動** |
| セキュリティチェック | 依存ライブラリ脆弱性 | Dependabot / `npm audit` / OWASP Dependency-Check | 週次（Dependabot）・リリース前 |

### 2.1 テストピラミッド

```
            ▲  E2E（主要シナリオのみ・少数）
           ▲▲▲  結合テスト（API ごとに正常系・主要異常系）
        ▲▲▲▲▲▲▲  単体テスト（ロジック網羅・多数）
```

E2E は時間がかかり不安定になりやすいため、ハッピーパス中心の主要シナリオに絞る。境界値・異常系は単体・結合テストで網羅する。

## 3. カバレッジ目標

| 対象 | 計測ツール | 目標（行カバレッジ） | CI での扱い |
| --- | --- | --- | --- |
| BE: Service 層 | JaCoCo | 80% 以上 | 下回ったら失敗 |
| BE: 全体 | JaCoCo | 70% 以上 | 下回ったら失敗 |
| FE: `features/` `lib/` | Vitest（v8 coverage） | 70% 以上 | 下回ったら失敗 |

> カバレッジは目安であり、数値達成のための無意味なテストは書かない。分岐・異常系・権限チェックが網羅されているかをレビューで確認する。

## 4. 機能別テスト観点

各機能の実装時に、少なくとも以下の観点のテストを作成する。（U = 単体, I = 結合, E = E2E）

### 4.1 ユーザー認証（AUTH）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 正常に登録でき、パスワードが BCrypt でハッシュ化されて保存される | ✓ | ✓ | ✓ |
| メール形式不正・ユーザー名形式不正・パスワード強度不足で 400 | ✓ | ✓ | |
| メール / ユーザー名の重複（大文字小文字違いを含む）で 409 | | ✓ | |
| 正しい資格情報でログインでき、アクセス/リフレッシュトークンが返る | ✓ | ✓ | ✓ |
| 誤ったパスワードで 401（メール存在有無を区別しないメッセージ） | ✓ | ✓ | |
| 期限切れ・改ざん・署名不一致の JWT で 401 | ✓ | ✓ | |
| リフレッシュでトークンがローテーションされ、旧トークンは猶予期間（30秒）を過ぎると再利用不可（全トークン失効） | ✓ | ✓ | |
| 更新の応答を受け取る前に画面を移っても（猶予期間内の再利用）ログアウトされない。ログアウト後は猶予期間中の旧トークンも使えない | ✓ | ✓ | ✓ |
| ログアウト後のリフレッシュトークンは使用不可 | | ✓ | |
| 未認証で書き込み API を呼ぶと 401 | | ✓ | |

### 4.2 スポット投稿 CRUD（SPOT）/ 写真（PHOTO）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 必須項目・文字数上限・エリアタグ数（1〜5）・写真枚数（0〜10）のバリデーション | ✓ | ✓ | |
| 作成・取得・更新・削除の正常系 | ✓ | ✓ | ✓ |
| 他人の投稿の編集・削除は 403 | ✓ | ✓ | |
| 存在しない ID は 404 | | ✓ | |
| 非公開投稿は本人以外に表示されない（一覧・詳細とも） | ✓ | ✓ | |
| 削除時に写真・いいね・コメント・ステータスが連鎖削除される | | ✓ | |
| 削除時に S3 削除処理が呼ばれる（S3Client をモック / S3Mock） | ✓ | ✓ | |
| 一覧のページング（カーソル）が重複・欠落なく動作する | | ✓ | |
| 署名付きURL発行: 許可外 Content-Type・サイズ超過で 400 | ✓ | ✓ | |
| 他ユーザーのプレフィックスの s3Key を指定すると 400/403 | ✓ | ✓ | |
| 写真をアップロードして投稿し、詳細画面に表示される | | | ✓ |

### 4.3 いいね（行ってみたい！）（LIKE）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 登録・解除ができ、件数と `likedByMe` が正しく返る | ✓ | ✓ | ✓ |
| 二重登録しても件数は1（冪等） | | ✓ | |
| 存在しない / 非公開の他人のスポットには 404 | | ✓ | |

### 4.4 コメント（COMMENT）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 投稿・一覧（古い順・ページング）・編集・削除の正常系 | ✓ | ✓ | ✓ |
| 空文字・1,001文字で 400 | ✓ | ✓ | |
| 他人のコメント編集は 403、削除はスポット投稿者なら可 | ✓ | ✓ | |
| 本文が HTML としてレンダリングされない（XSS） | ✓（FE） | | ✓ |

### 4.5 フォロー（FOLLOW）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| フォロー・解除、フォロー/フォロワー一覧と件数 | ✓ | ✓ | ✓ |
| 自分自身のフォローは 400（DB の CHECK 制約でも防止） | ✓ | ✓ | |
| 二重フォローは冪等 | | ✓ | |
| タイムラインにフォロー中ユーザーの公開投稿のみが新着順で出る | | ✓ | |

### 4.6 エリアタグ検索（SEARCH）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 単一タグ・複数タグ（OR）での絞り込み | | ✓ | ✓ |
| 親タグ指定で子タグの投稿も含まれる | ✓ | ✓ | |
| 存在しないタグ ID 指定時は 400 `AREA_TAG_NOT_FOUND` | | ✓ | |
| 並び替え（新着順・行ってみたい！数順） | | ✓ | |

### 4.7 ステータス管理（STATUS）

| 観点 | U | I | E |
| --- | --- | --- | --- |
| 「訪問済み」「行きたい」の設定・切り替え・解除 | ✓ | ✓ | ✓ |
| 「訪問済み」時のみ `visited_at` が設定される | ✓ | ✓ | |
| マイリストに自分のステータスのみ表示され、他人からは参照不可 | | ✓ | |

### 4.8 横断観点

| 観点 | レベル |
| --- | --- |
| エラーレスポンスが共通形式（`code` / `message` / `details`）で返る | I |
| すべてのレスポンスヘッダに `X-Request-Id` が付与され、ログの `requestId` と一致する | I |
| 認証済みリクエストのログに `userId` が出力される（`ListAppender` で検証） | I |
| ログにパスワード・トークンが出力されない | U / I |
| Swagger UI（`/swagger-ui/index.html`）・`/v3/api-docs` が 200 を返す | I |
| N+1 が発生していない（Hibernate Statistics でクエリ数を検証） | I |

## 5. CI 実行設計（GitHub Actions）

### 5.1 `ci.yml`（自動）

| 項目 | 内容 |
| --- | --- |
| トリガー | `pull_request`、`push`（全ブランチ） |
| ジョブ構成 | `lint` → `backend-test`（単体＋結合）／`frontend-test`（単体）→ `e2e` |
| DB | Testcontainers（`postgres:16`）。GitHub Actions の Ubuntu ランナーは Docker 利用可 |
| S3 | 結合テスト・E2E は Adobe S3Mock を使用（実 AWS には接続しない。LocalStack は 2026.03 以降認証トークン必須のため不採用） |
| E2E | `docker compose up` で DB・S3Mock を起動し、API と Vite のビルド成果物に対して Playwright を実行 |
| 成果物 | JUnit/JaCoCo レポート、Playwright レポート（失敗時のスクリーンショット・トレース）をアップロード |
| 失敗時 | PR のステータスチェックが失敗し、マージ不可（ブランチ保護） |
| 高速化 | Gradle / npm キャッシュ、`concurrency` で同一ブランチの古い実行をキャンセル |

### 5.2 `perf.yml`（手動のみ）

| 項目 | 内容 |
| --- | --- |
| トリガー | **`workflow_dispatch` のみ**。`push` / `pull_request` / `schedule` トリガーは絶対に設定しない |
| 実施時期 | 全機能完成時に1回（以降は大きな性能改修時に開発者の判断で実施） |

## 6. パフォーマンステスト（負荷テスト）

| 項目 | 内容 |
| --- | --- |
| 実施条件 | **全機能完成時に1回のみ、手動または指定トリガーで実施。** 日々の CI では実行しない |
| 理由 | トークン消費およびマシン負荷が大きいため |
| ツール | k6 |
| 環境 | 本番同等構成の staging 環境（本番環境には実施しない） |
| データ | ユーザー1万件、スポット10万件、いいね・コメント・フォローを比例生成（シードスクリプトで投入） |

### 6.1 シナリオと合格基準

| シナリオ | 負荷 | 合格基準 |
| --- | --- | --- |
| 新着一覧閲覧 `GET /spots` | 同時100 VU、10分 | p95 < 500ms、エラー率 < 1% |
| エリアタグ検索 `GET /spots?areaIds=` | 同時100 VU、10分 | p95 < 500ms、エラー率 < 1% |
| スポット詳細 `GET /spots/{id}` | 同時100 VU、10分 | p95 < 300ms |
| ログイン `POST /auth/login` | 同時20 VU、5分 | p95 < 800ms（BCrypt のコストを考慮） |
| 混合（閲覧80% / いいね10% / 投稿・コメント10%） | 同時100 VU、15分 | p95 < 500ms、エラー率 < 1% |

結果（p50/p95/p99、スループット、エラー率、RDS CPU）は `docs/perf_test_report.md` に記録する。

## 7. 品質ゲート（Definition of Done）

1つの機能（PR）を「完了」とする条件:

- [ ] 要件（[requirements.md](./requirements.md) の機能ID）を満たしている
- [ ] [4章](#4-機能別テスト観点) の該当観点の単体テスト・結合テストを作成した
- [ ] ローカルで全テストを実行し、オールグリーンを確認した
- [ ] CI（Lint・単体・結合・E2E）がすべて成功している
- [ ] カバレッジ目標を下回っていない
- [ ] Swagger UI に API 仕様（説明・リクエスト/レスポンス例・エラーコード）が反映されている
- [ ] ログレベル・MDC・機密情報マスクが [rules.md](./rules.md#5-ログ規約) に従っている
- [ ] DB 変更がある場合、Flyway マイグレーションと [database_schema.md](./database_schema.md) / [er_diagram.md](./er_diagram.md) を更新した
- [ ] PR を作成し、開発者のレビュー待ちにした（**マージは開発者が手動で行う**）

## 8. 不具合管理

| 項目 | 内容 |
| --- | --- |
| 管理場所 | GitHub Issues（ラベル: `bug`, `severity:high/medium/low`） |
| 再発防止 | 不具合修正時は、**先に不具合を再現する失敗テストを書き**、修正後にパスすることを確認する |
| 重大度の目安 | high: データ破損・セキュリティ・主要機能停止 / medium: 一部機能の誤動作 / low: 表示崩れ等 |
